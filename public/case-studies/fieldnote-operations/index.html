An inquiry workflow with fewer handoffs and clearer ownership.

A human-reviewed intake concept for a small service business: collect the right context, prepare a useful draft, and keep the final decision with a person.

Concept portfolio: fictional organizations and illustrative work, not commissioned client projects or measured business results.

Fieldnote Operations
Type

01 // THE STARTING POINT

A real-world problem, not a feature wishlist.

In this fictional scenario, requests arrive through several channels and the team copies information between an inbox, notes, and a task board. The pain is not simply typing. It is unclear ownership: nobody knows whether a request has been checked, assigned, or answered. Automating that confusion would only make it move faster.

The guiding objective

Turn an incoming request into an organized, reviewable next step.

The boundary: No autonomous sending, quoting, or changes to customer records.

02 // DISCOVERY & DIRECTION

Understand the journey before drawing the screens.

The proposed discovery follows a request from arrival to response. It identifies the minimum information needed, the person responsible for each decision, and the places where the team currently has to interpret missing context. Routine routing is separated from decisions that affect pricing, promises, or customer relationships.

The proposed workflow has four explicit states: Received, Needs Context, Ready for Review, and Approved. Each request has a source reference and an owner. Automation can prepare a summary and suggested response, but a reviewer decides whether it is accurate and appropriate before anything leaves the system.

03 // DECISIONS THAT MATTER

Every detail has a job.

Use a bounded first workflow

The first version handles only a defined request type. Unknown requests go to manual triage rather than being forced into the nearest category.

Make review meaningful

The review screen shows the source message beside the summary and draft. A person can edit, reject, or request more context instead of approving a black box.

Build a stop button into the process

The automation can be paused without losing the incoming request. Manual handling remains a supported path, not a failure state.

04 // THE WORK, UP CLOSE

From a vague starting point to a clearer experience.

This comparison describes the fictional starting scenario and the proposed design direction. It is not a claim about an existing client website.

STARTING SCENARIO

  • Requests copied into different personal notes.
  • A draft can be mistaken for a sent response.
  • Missing context is discovered late.

PROPOSED DIRECTION

  • One request record with an owner and source link.
  • Draft, approved, and sent are distinct states.
  • Missing information routes to a visible review queue.

A reviewable draft, not an autonomous promise

An example request says: “We need help updating the booking page before an event.” The draft summary records the affected page, desired change, and event date if supplied. If the date is missing, it is flagged—not guessed. A suggested response asks for the missing context and avoids inventing a price, delivery date, or confirmed scope.

What changes on a smaller screen?

Queue columns become a single ordered list. Status and ownership stay next to the request title. The reviewer opens one record at a time, keeping the original message and draft together rather than squeezing two unreadable panels onto a phone.

05 // UNDER THE HOOD

Practical technology. Explicit boundaries.

The design specifies a durable queue, idempotency keys for duplicate events, structured output validation, and a separate approval record. Access is limited to the minimum required source data. Any eventual send action must check that the current draft version was approved, so editing a previously approved draft invalidates its approval. This page documents a concept; no live mailbox or third-party automation is connected.

The awkward cases belong in the plan.

Duplicate events should resolve to the existing request. Unrecognized attachments are held for review rather than automatically executed or interpreted as trusted instructions. Provider timeouts move work into a retryable state with a visible error. Customer text is treated as untrusted input, not permission to change the workflow or access other records.

Verification plan

  • Review the critical journey on a small phone, tablet, and desktop.
  • Check keyboard order, visible focus, contrast, and meaningful image descriptions.
  • Exercise long content, missing optional fields, and invalid input states.
  • Verify every route, external destination, and recovery or escalation path.

This is the proposed acceptance checklist for the concept, not a report of a commissioned production release.

06 // DELIVERY & OWNERSHIP

Make the next update as considered as the first.

A polished launch is only part of the job. The proposed handoff explains what can be changed safely, what needs specialist help, and who owns the important accounts. Documentation should let a new maintainer understand the system without reconstructing the project from messages.

  • Workflow and ownership map with approved boundaries.
  • Request schema, review states, and example drafts.
  • Test fixtures for missing, duplicated, and unexpected inputs.
  • Pause, retry, escalation, and access-revocation procedures.

A sensible sequence

  1. Define: agree on the audience, scope, responsibilities, and acceptance criteria.
  2. Prototype: review structure, realistic content, and the critical interaction states.
  3. Build: implement the agreed patterns and record any decisions that affect maintenance.
  4. Validate: work through the checklist, resolve issues, and rehearse handoff.

07 // OUTCOMES WITHOUT THE GUESSWORK

Measure what matters. Don’t invent the numbers.

A real pilot would compare time spent reviewing drafts against manual handling, track correction rates, and check whether requests are consistently assigned. The evaluation should count rework and supervision time rather than reporting only how many drafts were generated.

What this example demonstrates

The proposed structure, original interface illustration, content patterns, and implementation reasoning show how this project could be approached. No conversion uplift, revenue increase, saved hours, or client testimonial is claimed.

08 // THE TAKEAWAY

A good system keeps people in control.

Useful automation makes responsibility clearer. A shorter workflow is not an improvement if nobody can tell what happened or who approved it.
